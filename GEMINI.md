## 🎯 Role & Technology Stack

- **Purpose**: Native iOS SDK component of the Beeping Platform ecosystem. Exposes a modern actor-based API to encode and decode short payloads transmitted over sound (audible + ultrasonic), running locally via ObjC++ bridge to `beeping-core` or remotely via the `beepbox` HTTP server.
- **Tech Stack**: `Swift 6 · Objective-C++ bridge · Actor Concurrency · SPM & CocoaPods`
- **Direct Consumers**: `beeping_flutter_ios`, Native iOS Apps
- **Minimum iOS Target**: iOS 15.0

## 🧪 Testing Strategy

- **Unit (legacy)**: XCTest
- **Unit (modern)**: Swift Testing (`@Test`, parametrized) — Xcode 16+ required
- **Snapshot**: `swift-snapshot-testing` (PointFree) for SwiftUI views + JSON serializations
- **Property-based**: `SwiftCheck` for encoder/decoder invariants
- **UI E2E**: XCUITest in `BeepingSampleApp` (sample app, BEE-78)
- **Coverage**: $\ge 80\%$ line coverage on target `Beeping`
- **Strict concurrency**: Compile with `-strict-concurrency=complete`, 0 warnings

## 🚫 Things to Never Do

- ❌ **Reintroduce singleton `[Beeping instance]` API** in the new Swift target.
- ❌ **Use `@unchecked Sendable` to silence strict concurrency warnings** — always fix the underlying data race.
- ❌ **Vendor new `.a` / `.dylib` / `.framework` binaries** from anywhere except a pinned `beeping-core` release tag.
- ❌ **Hardcode API keys or secrets** — always use `.env.local` or build arguments.
- ❌ **Skip `🧑‍🔬 Human QA Checkpoint`** for any task with observable effects (sample app UI, public API change, error messages).
- ❌ **Drop `PrivacyInfo.xcprivacy`** (Apple policy mandate).
- ❌ **Force-push to `develop` or `main`**.
- ❌ **Commit directly to `develop` or `main`** without pull request and CI validation.
